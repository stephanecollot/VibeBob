# VibeBob Marketplace

Community mods that anyone can install with one click from the VibeBob side panel.

## Publishing a mod

Open your mod in VibeBob → **dev** tab → **Publish to marketplace**.

VibeBob packages the mod, runs the same checks the robot will run, and opens a
prefilled GitHub issue. Tick the two declaration boxes, submit, and you're done:

1. A bot validates the submission and comments with the results, usually within a minute.
2. If the checks pass it publishes itself — no waiting on a maintainer.
3. It appears in everyone's Marketplace tab within about 5 minutes.

Your mod is published under your GitHub username, at
`marketplace/<your-username>/<slug>/`. Accounts less than 30 days old are held
for a maintainer to look at first, which keeps drive-by spam out.

**To ship an update**, bump `version` in the mod's manifest and publish again. The
version has to be higher than what is already published.

Mods larger than the URL limit can't be published in one click; VibeBob will tell
you and offer a zip to attach to a pull request instead.

### Structure

```
marketplace/
  <namespace>/          your GitHub username (or `official/`, maintainer-only)
    <mod-slug>/
      manifest.json
      mod.js
      mod.css           optional
      README.md
  catalog.json          generated — do not edit by hand
  blocklist.json        removed mods
```

`catalog.json` is regenerated by GitHub Actions on every change. Editing it by
hand just gets overwritten.

## What the checks look for

**These block publication:**

| Check | Why |
| --- | --- |
| `mod.js` parses the way the loader loads it | A mod that can't compile can't work |
| No `import` / `import()` | Mod source is inlined into a function body, so imports can't resolve |
| `apply(ctx)` and `cleanup()` are defined | The lifecycle contract — mods must be able to undo themselves |
| Only `manifest.json`, `mod.js`, `mod.css`, `README.md` | Nothing else gets written into the repo |
| `matches` are valid regexes, scoped to a site | A mod matching unrelated sites is a different trust class |
| `mod.js` ≤ 128 KB, `mod.css` ≤ 64 KB, bundle ≤ 256 KB | Keeps the catalog and review effort bounded |
| `version` is semver and higher than the published one | Makes updates auditable |
| Not byte-identical to something already removed | Closes the re-upload loop |

**These are reported but never block:** `eval`, `fetch`, `document.cookie`,
`innerHTML =`, references to hosts your mod doesn't declare, and a diff against
the previous version when it's an update. They're normal in plenty of honest
mods — they exist so a reviewer knows where to look.

Automated checks are mechanical, not a safety review. A keyword scan used as a
gate is trivially defeated (`window['ev'+'al']`), so we don't pretend otherwise.
What actually protects people is that every mod is attributable to a GitHub
account, installs are pinned to a reviewed commit and verified by hash, the
install screen shows exactly which sites a mod will run on, and anything harmful
can be pulled from every machine that has it.

## Moderation and takedowns

Mods are listed as soon as they pass the checks — nobody reads every submission
first. Anything harmful gets removed after the fact:

- Add the `takedown` label to a mod's submission issue. It leaves the catalog, and
  installed copies **disable themselves** within 6 hours (or immediately when
  someone opens the Marketplace tab), showing the reason and offering to delete.
- Remove the label to restore it. People who had it keep it disabled until they
  turn it back on themselves.
- For mods with no issue, run the **Takedown** workflow from the Actions tab.

A takedown cannot delete code that is already on someone's disk — installs are
their own copies. It can disable it and tell them why, which is the most a
marketplace with no server can honestly promise.

Found a problem with a mod? [Open an issue](https://github.com/stephanecollot/VibeBob/issues/new).

## File formats

### `manifest.json`

```json
{
  "name": "Human-readable mod name",
  "description": "What this mod does, in one sentence.",
  "matches": ["^https://example\\.com/.*"],
  "entry": "mod.js",
  "version": "0.1.0"
}
```

| Field | Required | Description |
| ------------- | -------- | ---------------------------------------------- |
| `name` | yes | Display name |
| `description` | yes | One-line summary |
| `matches` | yes | JavaScript regexes matched against the full URL |
| `entry` | yes | Always `"mod.js"` |
| `version` | yes | Semver string |
| `styles` | no | `"mod.css"` when you include a stylesheet |
| `author` | — | Set for you from your GitHub username |
| `issue` | — | Set for you from your submission issue |

### `mod.js`

Must export `apply` and `cleanup`:

```js
export function apply(ctx) {
  // Add your DOM mutations, event listeners, etc.
  // Use ctx.onCleanup() to register undo logic.
  // Use ctx.scope as a class prefix to avoid collisions.
}

export function cleanup() {
  // Undo everything apply() did.
}
```

Mods run in the page's main world, with the same access to the page as the site
itself. Keep them to what you'd be comfortable running on your own logged-in
accounts.

### `README.md`

A short description of what the mod does, with a screenshot if possible. One is
generated for you if you don't write one.
